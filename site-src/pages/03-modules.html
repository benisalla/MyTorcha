Chapter 3

Modules and layers

A model is a pile of tensors with requires_grad=True, plus a function that uses them. Module is just the tidy way to keep that pile.

Stacking layers: Sequential

```python import mytorcha as mt from mytorcha import nn mt.manual_seed(0) model = nn.Sequential(nn.Linear(2, 16), nn.ReLU(), nn.Linear(16, 3)) print(model) print(model.num_parameters()) print([name for name, p in model.named_parameters()]) ``` ```output Sequential( (layers.0): Linear(2, 16, bias=True) (layers.1): ReLU() (layers.2): Linear(16, 3, bias=True) ) 99 ['layers.0.weight', 'layers.0.bias', 'layers.2.weight', 'layers.2.bias'] ```

Count them yourself: 2×16 weights + 16 biases + 16×3 weights + 3 biases = 99. Linear stores its weight as (out_features, in_features) and computes x @ Wᵀ + b, exactly like PyTorch, so shapes and checkpoints translate one-to-one. ReLU has no parameters, so it doesn't appear in the list.

Writing your own Module

Subclass nn.Module, create layers in __init__, write forward. Calling the model calls forward.

```python import mytorcha as mt import mytorcha.functional as F from mytorcha import nn class MLP(nn.Module): def __init__(self, n_in, n_hidden, n_out): self.fc1 = nn.Linear(n_in, n_hidden) self.fc2 = nn.Linear(n_hidden, n_out) self.drop = nn.Dropout(0.1) def forward(self, x): return self.fc2(self.drop(F.relu(self.fc1(x)))) m = MLP(4, 8, 2) print(m) print(len(m.parameters()), m.num_parameters()) print(m(mt.randn(5, 4)).shape) ``` ```output MLP( (fc1): Linear(4, 8, bias=True) (fc2): Linear(8, 2, bias=True) (drop): Dropout(p=0.1) ) 4 58 (5, 2) ```

There's no super().__init__() to remember and nothing to register. That's because of how parameters are found.

How parameters() finds everything

Module.named_parameters() walks the module's attributes (vars(self)):

  • a Parameter is yielded;
  • a Module is walked recursively;
  • a list or tuple of Modules or Parameters is walked too, so self.blocks = [Linear(...), ...] just works;
  • a shared (tied) weight is listed only once, so the optimizer doesn't update it twice.
```python import numpy as np import mytorcha.functional as F from mytorcha import nn class Scale(nn.Module): def __init__(self, n): self.gain = nn.Parameter(np.ones(n)) # a hand-made trainable tensor def forward(self, x): return x * self.gain class Deep(nn.Module): def __init__(self): self.blocks = [nn.Linear(8, 8) for _ in range(3)] self.scale = Scale(8) def forward(self, x): for blk in self.blocks: x = F.gelu(blk(x)) return self.scale(x) print([n for n, _ in Deep().named_parameters()]) ``` ```output ['blocks.0.weight', 'blocks.0.bias', 'blocks.1.weight', 'blocks.1.bias', 'blocks.2.weight', 'blocks.2.bias', 'scale.gain'] ```

nn.Parameter is just a Tensor with requires_grad=True, stored as float32. nn.ModuleList also exists if you like the PyTorch spelling, but a plain list is fine.

Gotcha: modules hidden inside a dict, or created inside forward, are invisible to parameters(), so they will never train. If a layer refuses to learn, check that it shows up in named_parameters().

Training mode vs evaluation mode

Two layers behave differently while training. Dropout randomly zeroes activations only in training. BatchNorm normalises with the batch's statistics in training, and with its running averages in evaluation.

```python import mytorcha as mt from mytorcha import nn net = nn.Sequential(nn.Linear(3, 4), nn.BatchNorm1d(4)) net.eval() print(net.training, net[1].training) net.train() print(net.training, net[1].training) ``` ```output False False True True ```

train() and eval() set the flag on every sub-module. Forgetting model.eval() before measuring accuracy is a classic way to get noisy, slightly-too-low numbers. Trainer switches modes for you.

Saving and loading

```python import numpy as np import mytorcha as mt from mytorcha import nn net = nn.Sequential(nn.Linear(3, 4), nn.BatchNorm1d(4)) net(mt.randn(8, 3)) # one training-mode pass updates BatchNorm's running stats print(list(net.state_dict())) net.save("net.npz") # a plain NumPy .npz archive twin = nn.Sequential(nn.Linear(3, 4), nn.BatchNorm1d(4)).load("net.npz") net.eval(); twin.eval() x = mt.randn(2, 3) print(np.allclose(net(x).data, twin(x).data)) ``` ```output ['layers.0.weight', 'layers.0.bias', 'layers.1.weight', 'layers.1.bias', 'layers.1.running_mean', 'layers.1.running_var'] True ```

The state_dict holds parameters and buffers: non-trainable state such as BatchNorm's running_mean. A module declares its buffers in a class attribute _buffers = ("running_mean", "running_var"). The file is a standard .npz, so you can open it with np.load and look inside. No pickle and no mystery.

Initialisation: why v1's uniform(−1, 1) hurt

v1 drew every weight from uniform(−1, 1). Take 1,000 inputs of 784 pixels in [0, 1] through a 784 → 10 layer:

Initialisationstd of w·xtanh saturated (|a| > 0.99)
v1: uniform(−1, 1)8.5476%
MyTorcha default: U(±1/√fan_in)0.250%

A sum of 784 random terms has a standard deviation of about √784 times the size of one term. With pre-activations around ±8.5, three quarters of tanh units sit on a flat part of the curve with zero gradient (you saw this in the chapter 1 widget). The fix is to scale the weights by the fan-in. Every layer does it by default, using PyTorch's default rule. For other schemes, use mytorcha.init:

```python import mytorcha as mt from mytorcha import nn mt.manual_seed(0) w = mt.init.kaiming_normal_(nn.Parameter.empty(256, 784)) # He init, for ReLU nets print(round(float(w.data.std()), 4), round((2 / 784) ** 0.5, 4)) ``` ```output 0.0506 0.0505 ```
FunctionVarianceUse with
xavier_uniform_, xavier_normal_2 / (fan_in + fan_out)tanh, sigmoid

All initialisers fill in place (the trailing underscore) and use the global generator, so mt.manual_seed(0) makes runs reproducible.

Each one is a fused op in mytorcha.functional: f(x) and f′(x) are written side by side, and each is gradchecked and compared with PyTorch.

Try it

1. How many parameters does nn.Sequential(nn.Linear(784, 128), nn.ReLU(), nn.Linear(128, 10)) have?

101,770: 784·128 + 128 + 128·10 + 10. That's the MLP from the digits experiment in chapter 5.

2. You store your layers in self.layers = {"a": nn.Linear(2, 2)}. What does len(model.parameters()) return?

0. Dicts aren't walked (only Parameters, Modules, lists and tuples), so the optimizer gets an empty list. MyTorcha's optimizers refuse an empty list on purpose, so the mistake shows up immediately.

3. Why does Kaiming init use 2/fan_in while Xavier uses 2/(fan_in + fan_out)?

Xavier balances the variance of activations going forward and gradients going backward for symmetric activations like tanh. ReLU throws away the negative half of its input, which halves the variance, so Kaiming doubles the weights' variance to compensate.
